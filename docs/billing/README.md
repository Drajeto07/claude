# Billing: Stripe flows and webhook order

Payments are off until Boril's Stripe account exists (`docs/architecture/final-audit.md`). The code is complete and is tested against a stand-in for Stripe's API (`OfflineStripe` in `backend/tests/test_billing.py`): the real gateway, the real webhook signature check, nothing on the network. Code: `backend/app/services/billing_service.py`, `backend/app/billing/stripe_gateway.py`, `backend/app/api/billing.py`.

## How it works

- **Stripe is the source of truth.** A webhook is only a signal that a subscription changed. The app never takes the subscription's state from the event: it fetches the subscription from Stripe as it is now and writes that to the workspace's one `subscriptions` row. The plan the workspace gets is read from that row alone (`EntitlementsService.plan`): `active`, `trialing` and `past_due` give the plan, any other status gives the free plan.
- **Order does not matter.** Because every event leads to a fresh read, an event that arrives late, twice, or before the one that "should" have come first writes the same row. The only way an older state could win is two webhooks being handled at the same moment, each reading Stripe at a different time. The row therefore keeps when Stripe was read for it (`subscriptions.stripe_synced_at`, migration `d41f7a60c9e2`); a webhook holds the workspace (`hold_workspace`, the lock the plan checks use) while it writes, and a read older than the stored one is dropped.
- **Idempotency is by state, not by event id.** Handling an event twice rewrites the same values, so no ledger of event ids is kept. (A ledger would only save one fetch per duplicate, and would need its own table, a clean-up and a rule for events that failed half-way.)
- **Signature first.** The `Stripe-Signature` header is checked over the raw bytes, with Stripe's five-minute tolerance, before the body is read; a missing, wrong or old signature, an unset `STRIPE_WEBHOOK_SECRET` and a signed body that is no Stripe event all answer `400 invalid_webhook` with the same wording (nothing about why). A server without Stripe answers `503 billing_not_configured`. An event type the app doesn't use, or one that names no subscription, is answered `200` and ignored. A subscription Stripe no longer has is answered `200` (a retry would find the same); Stripe being unreachable is answered `502` so Stripe sends the event again.
- **One subscription per workspace.** Checkout is refused (`409 already_subscribed`) while the workspace has a live subscription; the portal is where a plan changes. If two checkouts opened together both complete, the row follows the later one and `billing.duplicate_subscription` is audited: the first subscription still bills in Stripe and has to be cancelled there (owner decision below).

## What needs the owner's Stripe dashboard

None of this is in code; it is settings in Stripe (use test mode first).

- **Webhook endpoint:** `https://<the API's host>/api/v1/billing/webhook`, with the signing secret in `STRIPE_WEBHOOK_SECRET`. Send these events: `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `customer.subscription.paused`, `customer.subscription.resumed`, `invoice.payment_failed`, `charge.refunded`, `charge.dispute.created`, `charge.dispute.closed`. Other events are answered and ignored.
- **Retries of failed payments** (Billing, Revenue recovery): turn on Smart Retries, and choose what happens when they run out. Recommended: **cancel the subscription**, so the workspace gets a clean new checkout. With "mark as unpaid" the old subscription stays open in Stripe and could be paid later, which would race a new subscription made meanwhile. Customer e-mails about failed payments are Stripe's, switched on there.
- **Customer portal** (Settings, Billing, Customer portal): list the Pro and Business prices under "Subscriptions can switch plans" (a price not listed can't be upgraded to), allow cancelling, and choose "at the end of the billing period" (the app handles "immediately" too). Set the business information and the return URL's page.
- **Prices:** one recurring price per paid plan, their ids in `STRIPE_PRICE_PRO` and `STRIPE_PRICE_BUSINESS`. The real limits and prices are Boril's decision (`plans.json` holds placeholders).
- **Refunds and disputes:** a refund or a lost dispute does not end a subscription on its own. Cancel it in Stripe if the customer should lose the plan; the app follows. The audit log has `billing.charge_refunded` and `billing.dispute` lines to tell the owner something needs attention.
- **Two subscriptions at once:** when the audit log says `billing.duplicate_subscription`, cancel (and refund, as decided) the one the row no longer follows in Stripe.
- **Stripe's API version:** the app reads subscriptions through the Python SDK (pinned in `backend/pyproject.toml`), which accepts the billing period on the subscription's items (API version 2025-03-31 and later) and on the subscription itself (older ones).

## Not covered, and why

- A subscription with several items (add-ons) is read by its first item.
- When a portal cancellation names a `cancel_at` date that is not the period's end, the billing page shows `currentPeriodEnd` (the period's end), not that date.
- A missed webhook (the endpoint down for longer than Stripe's three days of retries) is not repaired by a periodic reconciliation with Stripe; there is none yet. A subscription's next event, or a re-send from the dashboard, repairs it.
