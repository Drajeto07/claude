Branch `cloud/job-001-job-safety`, commit prefix `phase-05b-job-safety:`. Design reference: `docs/architecture/jobs.md`.

## Summary

All seven items are done and tested with the in-process queue (no Redis):

1. **Idempotency-Key** on the five job-creating POSTs, unique per user in the database.
2. **retry_count + exponential backoff**, for transient errors only.
3. **A timeout per job type**, with a message for people.
4. **`POST /api/v1/jobs/{job_id}/cancel`**, owner only, idempotent, cooperative for a running job.
5. **Stuck detection**: running past timeout + 60 s is queued again while attempts remain, else failed.
6. **Dead letter**: `dead_letter` flag + `failure_reason`, queryable, never swept.
7. **One Alembic migration** `c3a91f7d2b64` (down_revision `85211092fe4c`) with a downgrade.

## Design decisions

**Idempotency**
- Scope per user; unique index `uq_processing_jobs_created_by_idempotency_key (created_by, idempotency_key)`. NULL keys never collide.
- Format 1-128 of `A-Za-z0-9._:-`; invalid is `422 invalid_idempotency_key` through the error envelope.
- Same key + same request (hash of type, document, options and file bytes, `request_fingerprint`) returns the same job (202) and runs nothing.
  Same key + different request is `422 idempotency_key_reused`, never the other job. A failed job under a key is returned as failed; a new try needs a new key.
- Remembered as long as the job row (`JOB_RETENTION_DAYS`, 7); dead letters keep theirs.
- The replay lookup runs before the plan/content checks, so a repeat is answered even if the plan would now refuse a new job. Because an existing test
  (`test_a_file_over_the_plans_size_is_refused_before_it_is_read`) pins plan-size before content checks, the route order for a new job is unchanged;
  only the upload is read before the plan's document-count check in `import-file`.
- Concurrent duplicates: both pass the lookup, the unique index lets one insert, the other catches `IntegrityError`, rolls back and answers with the winner's job
  (or 422 if its request differed). Tested deterministically (lookup made blind) and with two real threads.

**Retries**: `JOB_MAX_ATTEMPTS=3`, wait `JOB_RETRY_BASE_SECONDS(5) * 2^retries` capped at `JOB_RETRY_MAX_SECONDS(300)`, no jitter (deterministic; see risks).
The runner returns the wait, the queue waits: `asyncio.sleep` in process, `arq.Retry(defer=...)` in the worker. Upload and text input are kept across retries.
- **Transient** (allowlist, `policy.TRANSIENT_ERRORS`): `ConnectionError`, `TimeoutError`, SQLAlchemy `OperationalError`/`InterfaceError`, Anthropic connection/timeout,
  rate limit and 5xx errors, botocore connection/timeout errors.
- **Never retried**: `DocxParseError`, `PdfParseError`, `UnsafeFileError`, `UnsupportedFileTypeError`, `PlanLimitError`, `JobError`, and every exception not on the list (a bug).
  `PERMANENT_ERRORS` wins when an exception is both.

**Timeouts** (s): import_text 300, import_file 600, format 600, export 300, extract_reference 300. A timeout is not retried (same input, same time). A thread
(PDF rendering) can't be killed; its result is dropped.

**Cancel**: owner only (`JobService.get` filters by user: another user's job gets the same 404 as a missing one, in `_REQUESTS`).
Cancelling `cancelled`/`succeeded`/`failed` returns the job as it is, 200 (no 409: a late or repeated cancel is a race, not a mistake). A pending job never runs and
loses its upload and text; a running one stops at its next `JobContext.report` (one conditional UPDATE, so a cancel can't slip between check and write) and
writes no result. If the work was already past its last check, the result is dropped at write time and an export's file is removed. New status value `cancelled`.

**Stuck**: deadline = type timeout + 60 s. Requeued (pending, `retrying`, `retry_count+1`) while attempts remain, else failed as dead letter with its upload removed.
Sweep every minute: arq cron `recover`, in-process `recover_in_process` task. A job is taken by compare-and-set on `(status, attempts)`, so an arq retry of a
crashed job and the sweep can't both run it; a worker retrying a still-"running" job takes it only past the deadline.

**Dead letter**: failed after the last attempt (transient exhausted, or stuck on the last attempt). `dead_letter=true`, `failure_reason` (e.g. `transient:ConnectionError`,
never document text), user-facing `error` "couldn't be finished after N tries". `GET /jobs?dead_letter=true`; `sweep_job_files` skips them. Text and upload are still removed
(no copy of the user's text is kept, SEC rules); only the row stays.

## Orchestrator review

- The orchestrator's first re-run of the full suite failed one test: `test_the_in_process_sweep_takes_a_stuck_job_back_and_runs_it`,
  with `no such table: processing_jobs`. On its own it failed 9 times in 25 runs. Cause: cancelling the sweep task while
  it is in the middle of a query invalidates its connection. Under `db_session_factory` (one in-memory SQLite connection
  through `StaticPool`), the connection that replaces it opens a new, empty database. The test now uses a SQLite file
  (25 of 25 runs pass), and the product code is unchanged. In production a pooled Postgres connection invalidated
  this way is just dropped.
- After the fix, the orchestrator's full-suite run gave 1796 passed, 1 skipped, 2 warnings in 258.19s.
- The model comment that named `app/jobs/retry.py` now points at `app/jobs/policy.py`.

## Risks and open questions

- **Real arq/Redis is not tested here.** What the code assumes: `arq.Retry(defer=seconds)` re-runs `run_job` and counts a try; `WorkerSettings.max_tries = JOB_MAX_ATTEMPTS + 3`
  (arq counts crash retries too, the runner gives up first); `job_timeout` = longest type timeout + grace so the job's own timeout fires first; `cron(recover)` runs every minute (arq's default
  second=0 with no minute/hour); a stuck job is queued again under id `{id}:retry{n}` because the first id's key may still be in Redis. If arq drops a queued job
  (Redis flush), a `pending` job with nothing queued is not detected: only `running` is swept. Worth a follow-up (sweep pending jobs older than N minutes).
- Cancel is cooperative: a single long AI call or a PDF render runs to its end before a running job stops. A document an import created after its last check
  stays in the user's list while the job says `cancelled`.
- No jitter on backoff; with several workers a burst of failures retries together. Easy to add.
- Dead letters are never swept, so they accumulate until an operator removes them: there is no admin endpoint or alert for them (follow-up).
- `failure_reason` on `JobOut` is deliberately not exposed (operators read the table).
- The stuck deadline uses the job type's timeout, so raising a timeout also raises the time a lost job waits.
- Plan checks for `import-file` now run after the file is read (needed to compute the request fingerprint); for a request that fails both, a different error may win.
- The frontend has no cancel button yet (the endpoint is ready); only `waitForJob` was fixed so a cancelled job doesn't poll for ever. `Job["status"]` now includes `cancelled`.
- Idempotency keys are not sent by the frontend yet; generating a key per user action and sending it on a retry is a follow-up.
