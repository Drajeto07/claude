# PDF-010..012 — PDF geometry layer, page classifier, inspection report (with P2E-008's fixtures)

Branch `cloud/pdf-010-012-pdf-foundation`, from `origin/feature/smartdoc-production-hardening` at `8966ec7`.

## Summary

A PDF import now also reads where everything is on the PDF's pages. This happens after the text read has accepted
the file. The editable import is unchanged: same elements, same content check, same refusals.

- **PDF-010, geometry layer** (`backend/app/parsers/pdf_geometry.py`). For each page it reads:
  - each character, with its font, size (as drawn, correct on turned pages), colour (`#rrggbb`), box and whether it
    is drawn invisibly (text render mode 3 or 7);
  - lines, rectangles and other curves, with line width and stroke and fill colours;
  - pictures, with their boxes and pixel sizes;
  - links (web / unsafe / internal with the target page / other action) and every other annotation, by subtype and box;
  - the media and crop boxes, the bleed, trim and art boxes when set, and the rotation.

  For the file it reads the outline (title, level, page), the form fields (name, kind), the metadata and whether XMP
  is present. pdfminer.six reads what is drawn and pypdf reads the file's structure. Boxes are in points on the page
  as shown, from its top left.
- **PDF-011, page classifier** (`backend/app/parsers/pdf_classify.py`). Each page is `text`, `scanned`, `hybrid` or
  `empty`, with a confidence, a reason and evidence:
  - text coverage and picture coverage (overlaps counted once, on a 100×100 grid);
  - visible and invisible characters (spaces excluded);
  - fonts, with the subset prefix removed;
  - picture and path counts.

  `hybrid` means text over a picture covering at least half the page. Confidence is 0.95 when the text is invisible
  (an OCR layer) and 0.6 when it is visible (it could be a scan with text added, or text on a background). A file's
  kind is the single kind of its non-empty pages; text and scanned pages together make `hybrid`.
- **PDF-012, inspection report** (`backend/app/fidelity/pdf_inspection.py`, model `backend/app/models/pdf_inspection.py`).
  - Each page is summed up as it is read, so a long file's characters are never all held in memory.
  - The summary is kept as `Document.pdfInspection` and sent with the document: upload, import job and later reads.
  - What each page summary holds: kind, confidence, reason, evidence, size, rotation, boxes, character count, fonts
    with sizes and counts, text colours, line, rectangle and curve counts, picture boxes, link counts by kind, and
    annotation counts by subtype.
  - What the file summary holds: outline, form fields, metadata **names**, XMP presence, PDF version, and
    `complete` / `stopped` / `notRead` / `structureProblem`.
  - Two new import-report keys, both described in `app/capabilities.py`:
    - `pdf.scanned_pages` (unsupported, a content change): scan pages whose words weren't imported.
    - `pdf.hybrid_pages` (lossy): text-layer pages, whose words may hold OCR mistakes.
- **P2E-008, fixtures** (`backend/scripts/make_pdf_fixtures.py` → `backend/tests/fixtures/pdf/*.pdf`, 9 files):

  | Fixture | What it holds |
  |---|---|
  | `text.pdf` | 2 pages; 4 fonts and 3 colours; an outline of 3 entries; a web link, a `javascript:` link and an internal link; a note |
  | `columns.pdf` | two columns |
  | `table.pdf` | a ruled 4×4 table and a shaded header |
  | `pictures.pdf` | two pictures |
  | `scanned.pdf` | an image-only page |
  | `hybrid.pdf` | a scan under an invisible text layer, a typed page and a bare scan |
  | `rotated.pdf` | pages at 0, 90 and 270 degrees, a landscape page, and a page with every page box |
  | `multilingual.pdf` | Bulgarian Cyrillic and Greek in embedded DejaVu Sans |
  | `form.pdf` | a text field, a check box and a choice |

  The fixtures are built with reportlab's invariant mode, so a rebuild gives the same bytes. A test checks this.

## Design decisions and why

- **pdfminer.six, not pdfplumber.** pdfminer.six is MIT and pulls in `charset-normalizer` (MIT, already locked) and
  `cryptography` (Apache-2.0 OR BSD-3-Clause, already in the dev lock through moto, so new only to the runtime lock).
  pdfplumber is also MIT but adds `pypdfium2`, a native PDFium binary, on top of pdfminer.six. The smaller set wins.
  - Pinned `pdfminer.six==20260107`.
  - Both locks recompiled with the commands in their headers. `uv` chose `cryptography==50.0.2` for the runtime lock,
    so the dev lock was moved from 50.0.1 to 50.0.2 (`--upgrade-package cryptography`) to keep the two the same.
  - `pip-audit` (2.10.1, via `uvx`) on both locks: "No known vulnerabilities found".
  - The shared venv here has pdfminer.six installed but still cryptography 50.0.1. CI installs 50.0.2 from the lock.
- **A second read, after the text read.** `read_pdf` runs first, unchanged. Every PDF it refuses today is still
  refused with the same message (tested: `scanned.pdf` still gets 400 `invalid_file` "No extractable text found...",
  and the malformed-PDF corpus still passes). The inspection never refuses an import:
  - If the geometry read refuses the file (too many objects, a pdfminer failure), the document still imports and its
    inspection says `complete: false` with the reason.
  - A bug in the inspection is handled the same way.
- **pypdf for the structure, pdfminer for the drawing.** pypdf is already hardened against the malformed-PDF corpus
  (SEC-011) and does outlines, named destinations and inherited form fields well. Page boxes, rotation and
  annotations come from pdfminer's own page objects, so their coordinates match the drawn content's.
- **Limits.** pdfminer has none of its own, so the read has these:
  - The text read's page cap and 2 MB content cap per page. These are read from `parsers/pdf.py` as module
    attributes, so one setting controls both reads. A form XObject's content counts again each time it is drawn.
  - 250,000 objects in the file: refused.
  - 200,000 characters, paths and pictures on a page; graphics states or forms nested 64 deep: stopped.
  - A 30 s time budget, checked on every drawn item and every `q`, as well as between pages.
  - pdfminer's flate, LZW and run-length decoders, swapped in its own module for bounded ones: 75 MB a stream (pypdf's
    limit) and 200 MB per read. The bounded flate decoder returns what decoded before damage (as pypdf does). This
    keeps pdfminer's byte-at-a-time repair from running; that repair is quadratic. Pictures are never decoded.

  Limits on the whole file refuse it with the text read's messages. A limit met on a page stops the read at that page,
  keeps the pages already read whole, and says why.
- **What the inspection leaves out, and why.**
  - Metadata values (titles and authors can be personal), form field values, and link addresses: links are only
    counted by kind, with `unsafe` decided by `security/links.py::safe_href`.
  - pdfminer's log is muted like pypdf's, since its messages can quote the file. Our own log lines name only the
    exception type and where it was raised.
- **Measured worst cases** (one page holding the full 2 MB of content, this container):

  | Page content | Geometry read | Text read |
  |---|---|---|
  | 160,000 rectangles | 9.7 s | 3.0 s |
  | 500,000 `q Q` | 6.9 s | 2.6 s |
  | 2 M characters | stopped at the item cap after 1.4 s | 0.8 s |

  The 30 s budget bounds files with many dense pages. Fixture reads take 2-110 ms each.
- **Classifier thresholds.**
  - A picture covering at least half the page counts as a scan of it.
  - A page with no text but some pictures is `scanned`: confidence 0.9 when the pictures cover half the page or more,
    0.6 below that.
  - Invisible text with no page-sized picture under it is `text` at 0.7.
  - These are heuristics and are written down as such. The PDF → editable phase can refine them with real files.

None. `pdfInspection` lives inside the document's JSON, defaults to `None` and needs no backfill.

## Risks and open questions

- **Upload time.** A large PDF upload can take up to 30 s more in the worst case, inside the synchronous upload
  request as well as the import job. Typical files take milliseconds.
- **Document size.** The inspection adds about 600 bytes a page to the stored document JSON (about 0.6 MB for a
  1,000-page PDF). Lists are capped: 20 fonts, 20 colours and 50 pictures a page; 1,000 outline entries and 1,000
  form fields.
- **Patching pdfminer.** Its decoders are swapped process-wide, in pdfminer's own module. Nothing else in the app
  uses pdfminer. A pdfminer upgrade must keep `pdftypes.zlib`, `pdftypes.lzwdecode` and `pdftypes.rldecode` as module
  globals; the decode tests would catch a change.
- **Fixture bytes depend on pinned versions.** The bytes depend on reportlab 5.0.1, Pillow 12.3.0 (its built-in
  font draws the scans) and, for `multilingual.pdf`, DejaVu Sans 2.37. A version bump means rebuilding the fixtures
  with `python -m scripts.make_pdf_fixtures`; the test says so.
- **No UI yet.** The inspection is in the API answer and the types, but the editor doesn't show it.

## Decisions for the owner

1. Whether the inspection should stay in the document JSON (as now, next to `importReport`) or move to its own table
   or asset once the PDF → editable phase stores layout.
2. The classifier thresholds (a picture covering half the page; confidences 0.95, 0.9, 0.7 and 0.6).
3. Whether metadata values (Title, Author) should be shown to the document's owner. Today only the names are kept,
   following the Word custom-properties rule.
4. The 30 s geometry budget on the synchronous upload route. It could be lower there and higher in the import job.
