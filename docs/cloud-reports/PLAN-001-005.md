# PLAN-001..005 Metering, plan limits, atomic AI operations

Branch `cloud/plan-001-005-metering`, from `origin/feature/smartdoc-production-hardening` at `8966ec7` (Alembic head
`b8534d3c4256`). Covers the rest of PLAN-003 (AI operations), PLAN-001 (usage units), PLAN-002 (plans as data) and
PLAN-005 (storage in bytes).

## Summary

- **PLAN-003, AI operations atomic.** Each AI call's operation is reserved before the call: counted and written under
  the workspace hold (`hold_workspace`) in a short transaction of its own, committed before the call, and given back if
  the call fails or is cut off. Two jobs with room for one call make one call (race test on SQLite and PostgreSQL). The
  same reservation (`UsageReservations`) serves exports. Consistent with JOB-001: a retried job counts once.
- **PLAN-001, usage units.** `backend/app/billing/units.py` defines every unit once with the entitlement that limits
  it: documents, exports, PDF pages (counted at PDF import), OCR pages, translation characters, batch jobs (the last
  three named, counted once their features exist), AI operations, storage, and templates. `GET /api/v1/usage` and
  `GET /api/v1/billing` list each (`units`) with the plan's limit; the billing page draws them.
- **PLAN-002, plans as data.** Every limit and the default plan live in `billing/plans.json`; new monthly limits are
  placeholders; an unknown or missing entitlement stops startup. A test checks every entitlement the code reads is
  defined for every plan; a static AST scan of `app/` finds no comparison with a plan's id (one was there and is gone).
- **PLAN-005, storage in bytes.** Documents and older version rows are measured with `octet_length` (PostgreSQL) /
  `length(CAST(x AS BLOB))` (SQLite) instead of `length()` of text, which counts characters on both. Tests compare
  the figure with the bytes actually stored, on both databases.
- **No migration**: a reservation is the `usage_records` row that counts the use (deleted again to give it back).

## Design decisions

**Reservation = the usage row, in its own transaction (`UsageReservations`, `services/entitlements_service.py`).**
`take(unit, quantity)` opens a session of its own (the job runner's session factory; for a request, a sessionmaker on
the request session's engine), holds the workspace, counts the month, refuses with `PlanLimitError` when there's no
room, adds the `usage_records` row and commits, all before the call. `give_back(id)` deletes that row in its own short
transaction. Why its own transaction: the job's (or request's) transaction is long and is rolled back when the work
fails, so holding the workspace in it would serialise every job of a workspace for minutes, and the count would go
with a rollback. Why no table: the row that reserves is the row that counts; nothing has to be "confirmed" later, so a
crash can't leave a reservation that neither counts nor expires. Cost: two short transactions per AI call (and one
more when a call fails).

**AI calls (`metered()`, `MeteredAIProvider`).** Before each call: `take(AI)`; a refusal becomes
`AILimitReachedError`, so every AI step falls back exactly as before (work that is all AI is still refused up front by
`check_ai`, 402). After a call that raised -- any `BaseException`, so a `CancelledError` too -- the operation is given
back; a call that returned stays counted. `BudgetedAIProvider` wraps the metered provider, so a call the budget refuses
reserves nothing, and one it cuts off (its `wait_for`) is given back. The request path and the job runner use the same
`metered()`. The two endpoints that committed only "the AI call's usage" (style analysis, reference extraction) no
longer need to; that commit is gone. Side effect (wanted): a request's AI calls are now counted even when the request
then fails; before, they went with its rollback.

**JOB-001 semantics, decided and tested:**
- retry: reserved, the call failed transiently, given back, the job retried, reserved again, made: **one** count
  (`test_a_retried_job_whose_call_failed_transiently_counts_its_call_once`);
- the job's own timeout cuts a call off: given back, **not counted** (the user got nothing; the same rule as for any
  failed call) (`test_a_call_cut_off_by_the_jobs_timeout_is_not_counted`);
- cancelled mid-call: a cancel is cooperative (noticed at the job's next `report`), so the call under way completes;
  it was made, so it **counts**, and the job stops right after
  (`test_a_job_cancelled_during_its_call_keeps_the_completed_call_counted`);
- a call that completed in an attempt that later failed stays counted (as before: JOB-001's
  `test_the_calls_a_failed_attempt_made_are_still_counted` still passes);
- a worker that dies between reservation and outcome leaves the reservation counted: a use that may have happened is
  counted, none is given away. At most one operation per call in flight at the crash.

**Exports.** An export is reserved before it is built: the job's `_export` via `JobContext.reserve_for_result`, kept
only if the runner writes the job's result and given back on every other outcome (failure, retry, timeout, cancel, a
result dropped because the job was cancelled after its last check, a run cut off from outside); the direct
`GET /documents/{id}/export/{docx,pdf}` via `reservations.held(EXPORT)`, given back if the build raises.
`check_export` also refuses early (no hold) when the month's exports are used up, so the job route answers 402 before
a job exists. `record_export` no longer writes a usage row (the reservation is the count).

**PDF pages.** Counted when a PDF is imported, every page, with the document it becomes: `create_from_bytes` counts
the pages (`pdf_page_count`, which opens the file through the same `_open`/`_refusing` code as `read_pdf`, so a
malformed, encrypted or too-long file is refused with exactly the same message), refuses early when the month has no
room (before any page is read or the AI is asked), and `create` checks again under the hold it already takes for the
document count and writes the `pdf_pages` row in the document's own transaction. No reservation needed: the count and
the document commit together, or neither does, so a retried import counts once.

**Units (PLAN-001).** One `UsageUnit` per unit: API key, label, entitlement, metric (counted per month) or none
(measured now), measure (count/bytes), scale (MB -> bytes for storage), counted (False for OCR, translation, batch).
Documents keep today's meaning (documents held now, `maxDocuments`), not the brief's "documents per month"; the monthly
`documentsCreated` counter is still in `GET /usage`. Templates are a unit too (they have a limit). `UsageOut` and
`BillingOut` keep every existing field (the dashboard and tests read them) and add `units`.

**Plans as data (PLAN-002).** plans.json gains `defaultPlan` ("free") and, per plan, `maxExports`, `maxPdfPages`,
`maxOcrPages`, `maxTranslationCharacters`, `maxBatchJobs` (per calendar month). Today's values are kept where they
existed (documents 25/500/null, file size, AI 100/2000/10000, templates, storage); the new ones are the brief's section 64
hypotheses: exports 25/500/10000 ("high" for Business), PDF pages 20/500/5000, OCR pages 5/100/1000, translation
characters 10,000/500,000/5,000,000, batch jobs 0/50/500 (Free has "no batch"; Pro/Business numbers are mine: the
brief gives none). `Entitlements` forbids unknown fields and has no defaults, so a typo or a missing entitlement stops
startup. `FREE` is kept as the name for `DEFAULT_PLAN` (tests import it). `price_ids` compared a key with `FREE`; it
now relies on there being no `STRIPE_PRICE_FREE` setting (a plan without a price can't be bought), so the scan's
allowlist is empty. The subscription model's Python default is `DEFAULT_PLAN` (no schema change).
Not moved: `PRIORITY_HEAD_START` (10 minutes, `jobs/queue.py`) is how priority is implemented, not a plan's limit;
`MAX_UPLOAD_SIZE_MB` and the AI budget per job are the server's own caps.

**Storage (PLAN-005).** Counted: documents (their JSON as saved, in bytes), version history as stored (compressed
bytes; an older uncompressed row as its JSON text in bytes), assets (pictures and the Word files imports were made
from, the "kept originals"; `size_bytes` is the stored file's length). Not counted, by decision: a job's upload
(removed when the job ends) and an export's file (kept for the job's 7 days, `JOB_RETENTION_DAYS`): neither is
something the workspace keeps, and counting exports would make storage go up and down with downloads. Templates' JSON
isn't counted either (small, and limited by `maxTemplates`). `octet_length` is a SQLAlchemy function element in
`app/db/types.py`: `octet_length(x)` on PostgreSQL, `length(CAST(x AS BLOB))` on SQLite (SQLite's own `octet_length`
only exists since 3.43). On PostgreSQL a `jsonb` document is measured as its text rendering (what `data::text`
gives), which is the closest thing to "the document's bytes"; its on-disk size (`pg_column_size`, TOAST-compressed)
would vary with PostgreSQL's storage, not with the document. PERF-004's retention rule uses the same `stored_bytes`,
so on PostgreSQL an old uncompressed row is now measured in bytes there too.

## Migrations

None. A reservation is a `usage_records` row (that table has RLS since `4cbc55236361`); the new metrics are new
values of its `metric` string. Alembic head stays `b8534d3c4256`, so nothing here collides with W1's migration.

## Risks and open questions

- A worker killed during an AI call leaves that call's operation counted (at most one per call in flight). An export
  reserved by a job whose worker dies stays counted too, and the stuck sweep's rerun reserves again, so such an export
  can count twice. Only on a crash; giving back the reservations of dead attempts would need a reservation table with
  the job's id (a migration), which didn't seem worth it.
- Two extra short transactions per AI call (reserve; on failure, give back). Negligible against an AI call's latency.
- On SQLite (tests, development) the reservation's session needs the write lock while the job's own session holds no
  write: true today (every AI call comes before the job writes, or after a committed `report`). A future AI call made
  after an uncommitted write would wait the 5 s busy timeout and fail on SQLite (and wait for the row lock on
  PostgreSQL only if that write held the workspace). Nothing does that now; the full suite exercises every AI path on
  separate connections.
- The new Free limits (25 exports, 20 PDF pages a month) are real restrictions where there were none: placeholders,
  but they apply once deployed.

## Decisions for the owner

1. The real numbers in plans.json (all placeholders), in particular the new monthly ones and batch jobs for Pro/Business.
2. Whether "documents" should become documents per month (the brief) instead of documents held (today's `maxDocuments`).
3. Whether a call cut off by a timeout should count (cost was possibly incurred) -- today it doesn't.
4. Whether templates' JSON should count as storage.
