# PERF-002 benchmarks and PERF-006 UTF-8 JSON storage

Branch `cloud/perf-002-006-benchmarks-utf8-json`, from `feature/smartdoc-production-hardening` at 370ed49.

## Summary

- **PERF-002**: `backend/scripts/benchmark.py` measures time (best and median of 3 runs) and Python peak memory
  (tracemalloc) of importing every golden and Word fixture, Word and PDF export, save (`PUT /content`) and load
  (`GET`), on synthetic documents of 500, 2000 and 5000 blocks, a 500x8 table and 50 pictures. Each case runs in a child
  process with a time limit. The baseline was measured on 370ed49, before any PERF-006 change, and committed
  (`docs/performance/benchmarks.md` and `.json`).
- **PERF-006**: document JSON is stored as UTF-8 instead of `\uXXXX` escapes. A stored Bulgarian text is 49.6% smaller
  on SQLite; a real fixture with a little Cyrillic, 1%. Old escaped rows still read. On Postgres (`jsonb`) the stored
  bytes do not change; the text sent to the database does.

## Design decisions

- **Every case in a child process** (`python -m scripts.benchmark --worker ...`) with `subprocess.run(timeout=...)`: a
  thread can't be killed, and the 500x8 table Word export is known to take minutes. `--timeout` (default 600 s) kills
  and reports; `--quick` and `--only` leave things out. A run slower than 20 s is timed once and its memory is not
  measured (tracemalloc would make it several times slower).
- **Export, save and load go through the API** (TestClient, a temporary SQLite file, the same dependency overrides as
  `tests/conftest.py`, `DATABASE_URL` forced to a temporary SQLite file in the child). So an export includes the load
  from the database and the stored pictures, which is what a user's download does. The request body is encoded before
  the timer starts. Import is `build_document_from_docx` in-process.
- **Synthetic documents are document-model JSON** written in the script (the shape the editor sends), in Bulgarian, so
  the stored JSON has the characters PERF-006 is about; the 50 pictures are Pillow noise PNGs sent as `data:` URIs the
  way the editor pastes them (the save moves them into asset storage). Ids are uuid5, so every run saves the same document.
- **`dump_json` keeps `json.dumps` otherwise identical** (separators, key order, NaN; SQLAlchemy passes no `default=`
  or `sort_keys`) and only sets `ensure_ascii=False`. One addition: an unpaired surrogate in a text can't be encoded as
  UTF-8 (the SQLite driver would raise on binding), so such a text keeps the escaped form. The model strips surrogates
  from text fields (`XmlText`) but `preservedAttributes` is free-form. It is a regex scan, no copy of the text.
- **One `make_engine` in `app/db/session.py`** that every async engine goes through, including the tests' and the
  benchmark's. Without it a test engine could silently keep the default and the tests would not prove what
  production stores. The engine for Alembic (`alembic/env.py`) writes no JSON (schema only; the data migrations are SQL
  that reads JSON paths, which is the same for both forms) so it was left alone; `scripts/e2e_server.py`,
  `migrate_json_documents.py` and `verify_database.py` use the app's engine (`get_engine`) and are covered. Job payloads, results and
  the version history are JSON columns on the same engine, so they are covered; the only other `json.dumps` calls in the
  app are a hash, a log line and an in-memory scan, not storage.
- **Postgres**: all JSON columns use `JSONVariant` (`JSON` on SQLite, `JSONB` on Postgres); none is `Text`. `jsonb` keeps a
  parsed binary form that holds the letters either way, so its storage does not change; only the text sent by the app
  does. Not measured on Postgres (no real database).

## Tests added

`tests/test_utf8_json_storage.py` (9): the serializer writes letters and otherwise equals the default;
an unpaired surrogate keeps its escape; the application's engine and `make_engine` use it; a stored document
(documents and versions rows, raw SQL, after create and after an editor save) holds the letters and no `\u04`; any
JSON column (a job's payload and result) is written as letters; **a row written with escapes by raw SQL still reads
through the model and the API and is rewritten as letters on the next save**; a Bulgarian text takes under 60% of
the bytes of its escaped form; a GET response is UTF-8 letters (`application/json`, body bytes contain the letters
and no `\u04`).
`tests/test_benchmark_script.py` (4): synthetic documents are what their names say; import, save/load and both
exports run on a tiny case; a case over its time limit is reported as timed out; the report lists what did not finish.

Results: `tests/test_utf8_json_storage.py tests/test_benchmark_script.py tests/test_versioning.py tests/test_usage.py`:
32 passed. Full suite, base 370ed49 on this machine: **1725 passed, 1 skipped** (258 s), the same as the owner's.

## PERF-006 numbers

Stored `documents.data` bytes, escaped (before) to UTF-8 (after), SQLite:

| Document | Before | After | Smaller |
|---|---:|---:|---:|
| 500 Bulgarian blocks | 1,117,596 | 564,084 | 49.5% |
| 2000 blocks | 4,463,490 | 2,248,418 | 49.6% |
| 5000 blocks | 11,154,890 | 5,617,738 | 49.6% |
| table 500x8 | 1,408,015 | 1,199,423 | 14.8% |
| 50 pictures (captions) | 111,055 | 77,743 | 30.0% |
| `12-complex.docx` | 49,582 | 49,072 | 1.0% |
| `r01-university-paper.docx` | 79,160 | 69,984 | 11.6% |

Over all 37 imported fixtures: 1,829,891 to 1,811,659 bytes (1.0%). Real documents hold a lot of ASCII
besides text, so the saving follows the share of Cyrillic prose.

Save and load after PERF-006 (3 runs, best; baseline in brackets): save 500 blocks 88 ms (69), 2000 blocks 259 (299), 5000
blocks 842 (852), table 226 (204), pictures 122 (101); load 22 (24), 67 (77), 157 (159), 67 (53), 15 (11). Two earlier after-runs
gave 68 to 98 ms and 819 to 1010 ms for the same cases, so none of this is beyond the noise. Python heap peak of a save grew
about 20% (500 blocks 6.9 to 8.3 MiB, 5000 blocks 68.8 to 81.5 MiB; load unchanged). Cause, checked on its own: the sqlite3
driver makes a UTF-8 copy of a text that is not pure ASCII when binding (16 MB extra for a 3.4M-character text) and none for
an ASCII one. `dump_json` itself: 25 ms to 33 ms for a 4 MB document, and a smaller peak (10.2 to 6.1 MiB).

## Risks and open questions

- Python heap peak of a save is about 20% higher on SQLite (the driver's copy); the owner may judge it worth the
  halved rows and transfer. On Postgres the driver encodes the text to UTF-8 anyway; not measured.
- Nothing was run against Postgres. The claim that `jsonb` storage does not change is from how jsonb works (parsed
  binary), not from a measurement.
- `usage_service.storage_bytes` counts characters (`length(cast(data as text))`), not bytes, so the quota never counted
  bytes; on SQLite a Cyrillic document now counts about what it did on Postgres. Not changed (out of scope).
- Old rows are not migrated: each is rewritten as letters on its next save. A one-off script could do it if the
  owner wants the old versions smaller too (every undo step keeps its own row).
- The baseline file says "git commit 370ed49"; the after-run says 024783b. The benchmark script itself changed between
  the two (its harness uses `make_engine`, which the base commit does not have), which is why the baseline was run
  from the first commit's script and the harness change is in the PERF-006 commit.
- Timings are from a shared 4-core machine; the committed numbers are a reference for the next run on this class of
  machine, not absolute.

## Not done

- No `--no-memory` option, no chart/diff tool between two `benchmarks.json` files (they are plain JSON).
- The after-run did not repeat import and export (PERF-006 does not change them; export includes a database read
  but not a write). The table's Word export (4 minutes) belongs to PERF-001's branch.
- Follow-ups for others: PERF-001 (500x8 table export, 247 s; PDF of the same takes 1 s) should re-run
  `python -m scripts.benchmark --only export` and commit the new numbers.
