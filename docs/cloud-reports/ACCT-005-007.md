## Summary

- **ACCT-005, deleting an account.** `DELETE /api/v1/auth/account {password}`: the password checked with
  `AuthService.password_is`, counted like sign-ins (the per-account rate limit and the ACCT-007 wait); the WIP
  branch's policy (`services/account_deletion.py`) applied in one transaction; then, after the commit, the files
  deleted from storage in a background task (a failure logged by key, never raised), the goodbye e-mail
  (`messages.account_deleted`), an audit line `auth.account_deleted` with counts only, and the cookie cleared.
  Refusals: 400 `wrong_password`, 409 `subscription_active`, 409 `workspace_has_members`. "Delete your account" on
  `/settings/account` says what goes, asks for the password and a typed `delete my account`; afterwards
  `/login?deleted=1` says the account is deleted.
- **ACCT-006, sessions.** `GET /auth/sessions` (browser name from the User-Agent, created, last used, current; no
  IP), `DELETE /auth/sessions/{id}` (one; this one's cookie cleared if it is this one), `POST
  /auth/sessions/sign-out-others`. `sessions.last_used_at` written at most every 5 minutes. Ended sessions are
  deleted 30 days after they ended, used/expired account tokens 7 days after, known browsers after 400 days unused
  (`config.py`), hourly: in process (`sweep_forever`) and in the arq worker (`sweep_accounts`, minute 47).
- **ACCT-007, suspicious sign-ins.** Written down in `docs/security/README.md` and implemented: no lockout (the
  per-account rate limit stays); after 3 wrong passwords for an account within 15 minutes, each next try waits 1,
  2, 4, at most 8 s before the password is checked (`security/sign_in_delay.py`; injectable `sleep` and `clock`,
  the tests never sleep); a sign-in from a browser the account hasn't used e-mails the owner the browser's name
  and the time (UTC), no IP or place. A browser is recognised by a 256-bit random `smartdoc_device` cookie
  (HttpOnly, Secure, Lax, 400 days), stored per account as its SHA-256 in `known_browsers`.

## Design decisions and why

- **Audit line without personal data.** `auth.account_deleted` carries only counts (workspaces, documents, files):
  no user id (pseudonymous, it would link the line to earlier ones with an IP), no address, no IP. The request id
  is on the line, so the request can still be found. Failed attempts (`auth.account_deletion_failed`) keep the user
  id and IP like other failed actions, since the account still exists then.
- **Refusal codes.** 400 `wrong_password` (as ACCT-004), 409 `subscription_active`, 409 `workspace_has_members`,
  through the error envelope (`HTTPException(detail={code, message})`).
- **The delete route answers 204 and clears the cookie** in the same response; files and e-mail are background
  tasks after the commit, so a storage outage can't undo or block a deletion; a failed key is logged at WARNING.
- **Sessions: last use to 5 minutes.** `resolve_session` selects whether the row is stale in SQL and writes only
  then, committing that alone (nothing else is pending at that point), so most requests write nothing.
- **Browser names** are family + system only (no version, never the raw header), from a small ordered marker list
  (no new dependency). The IP stays in `sessions.ip_address` as before but is never returned.
- **Sign out one session**: 404 `not_found` for another user's or an ended one, the same body (security suite).
  Signing out this one from the list clears its cookie.
- **Retention** (in `config.py`, documented in the security README): ended sessions 30 days, used/expired account
  tokens 7 days, known browsers 400 days unused. Hourly: in process with the job sweep, in the worker as its own cron
  job (`sweep_accounts`, minute 47, apart from `sweep` at 17).
- **The wait (ACCT-007)** is before the password check, right or wrong, so a guesser who drops slow answers learns
  nothing from a fast one; the right password still gets in and clears the count, so it is never a lockout.
  Keyed by a hash of the address in the same backend as the rate limits (memory or Redis, fail open), so an address
  without an account waits the same (no enumeration by timing). Wrong passwords in change-password and delete-account
  count too. 3 free failures, 15-minute window, 1-2-4-8 s, cap 8 s (max 30 by validation).
- **"A browser it hasn't used before"** = no `known_browsers` row for (user, SHA-256 of the `smartdoc_device`
  cookie). The cookie: 256 random bits, HttpOnly, Secure (per `SESSION_COOKIE_SECURE`), SameSite=Lax, 400 days
  (the browsers' cap), set again at each sign-in. A value not shaped like ours is replaced. The account's sign-up
  browser is recorded silently. The e-mail says the browser's name and the time in UTC, links to the account page
  and to "forgot password"; no IP and no place. Clearing cookies or a private window counts as a new browser.
- **Existing accounts after the deploy** have no known browser yet, so each one's first sign-in from any browser
  e-mails once. Chosen over staying silent (which would let an attacker's first sign-in after the deploy pass
  unreported); see owner decisions.

## Risks and open questions

- A job still running in a deleted workspace may write its export file after the deletion's file sweep ran
  (`jobs/{id}/output`); that file is then orphaned in storage (the job's row is gone). Rare (the user deletes the
  account during an export); a periodic orphan sweep of storage would catch it.
- The Stripe customer of a workspace with a cancelled-at-period-end plan stays at Stripe; later webhooks for it are
  ignored (`billing_service.sync` logs "belongs to no workspace here").
- The wait and the rate limits live in process memory by default: with several API processes and no Redis, each
  counts on its own (as the rate limits already do).
- Waits hold a request open up to 8 s (async, no worker thread blocked).
- `DELETE` with a JSON body: fine for browsers, fetch and the app's proxies; a proxy that drops DELETE bodies would
  turn it into a 422.

## Decisions for the owner

- The retention periods (30 / 7 / 400 days) and the wait (3 free, 15 min, cap 8 s).
- The one-time new-browser e-mail for existing accounts after the deploy (alternative: stay silent until an
  account has a known browser).
- Whether the deletion's audit line should carry the user id after all (traceability vs. a pseudonymous id).
- Whether to delete the Stripe customer on account deletion (needs the Stripe API; not done).
- Typed confirmation phrase `delete my account` (English-only, like the rest of the UI).
